# Мета проекту №1 - розробити Автопілот MAVLink з релізацією Failsafe протоколу донаведення до цілі
# Мета проекту №2 - розгорнути проект на реальному залізі, Raspberry PI Zero + ESP 32 S3

## Архітектура проекту

Система складається з чотирьох процесів, які спілкуються між собою по MAVLink v2 (UDP на хості, UART на залізі). Кожен процес відповідає за свою роль і нічого не знає про внутрішній устрій інших.

### Процеси

1. Дрон (drone_sim.cpp / main.cpp прошивка на ESP32) - фізика руху дрона (позиція, курс, швидкість) і обробка вхідних команд керування. Логіка одна й та сама на хості і на залізі (DroneNode), різниться лише транспорт (UDP чи UART) і спосіб виводу телеметрії. Фактично є виконавцем отриманих команд.

2. Автопілот (autopilot.cpp) - основний модуль: приймає телеметрію дрона і координати цілей, рахує точку упередження (балістика + наведення), формує команди керування, стежить за зв'язком з оператором і переходить у Failsafe при його втраті, звітує оператору про хід місії.

3. Оператор (operator_simю.cpp) - імітація оператора (GCS): вмикає/вимикає автопілот, надає координати цілей, може надсилати власні команди керування, приймає статус місії, записує лог симуляції (simulation.json).

4. serial_bridge - міст UART <-> UDP. Потрібен лише коли дрон живе на окремому пристрої без мережі (ESP32): пересилає MAVLink-кадри в обидва боки.

### Потік даних

Способи передачі даних - UDP на ОС, UART на залізі.

- дрон -> автопілоту: телеметрія, heartbeat. Дрон не знає про існування оператора, шле лише в один бік - на UART (serial_bridge) чи UDP-порт автопілота (у варіанті запуску з хоста про всяк випадок дублює ще й на UDP-порт GCS, історично лишився спосіб).
- serial_bridge -> додатково дублює кожне повідомлення від дрона оператору (GCS), сам дрон про це дублювання не знає.
- оператор -> автопілоту і дрону: heartbeat, команда enable, координати цілей, ручне керування.
- автопілот -> дрону: розраховані команди керування.
- автопілот -> оператору: статус місії, покроковий лог симуляції, повідомлення про скид і завершення місії.

## Про підхід та причини прийнятих рішень

Підхід до виконання задачі - "best effort" з врахуванням наявних умов.

1. Оператор надсилає цілі дрону, дрон не має власних сенсорів для отримання інформації по цілям, отримує їх ззовні. Єдиним логічним місцем є оператор (GCS), тому що він володіє повною ситуаційною обізнаністю та здійснює керування. Дрон та модуль автопілота нічого не знають про цілі за задумом, оскільки обидва не мають сенсорів для їх визначення.
2. Failsafe сценарій - автопілот отримує інформацію по цілям від оператора, а цілі є рухомими, точка розрахунку куди виконувати скид накопичує похипку з кожною секундою відсутністю зв'язку та актуальних координат цілей, на такий випадок реалізовано два механізми:
  2.1 Дрон близько до точки скиду - якщо зв'язок пропав, похипка ще низька (наприклад зв'язку нема X секунд), а дрон вже досяг точки скиду - можна виконувати скид, оскільки похипка невелика, є шанс влучити у ціль.
  2.2 Дрон далеко від точки скиду - в такому випадку похипка збільшується суттєво без відновлення зв'язку, і щоб не марнувати снаряд, автопілот переходить у режим очікування зв'язку з оператором. Якщо зв'язок відновлено - продовжує місію.
  * у реальному житті можна було б реалізувати повернення дрону на GCS, якщо зв'язку нема > X часу.
3. Місія починається тоді коли автопілот отримав перше повідомлення від оператора, надіслав дрону, а той відповів. Це важливо для синхронізації годинників процесів дрону і оператора, та коректної роботи алгоритмів та сценаріїв. Також коли автопілот дає дрону команду старту місії - дрон виконує рестарт, щоб почати місію "з чистого нуля", зокрема щоб внутрішній годинник дрона почав роботу з нуля.


## Сценарії виконання

Усі сценарії лежать у папці homeworks/20_autopilot_MAVLINK_course_project/data/scenarios.
Детальніше про кожен сценарій у файлі сценарію.


1. 01_clean_attack - базовий сценарій, оператор ввімкнув модуль автопілота, та почав надсилати дані про цілі. Автопілот сам доводить атаку до кінця.

2. 02_operator_interrupt - оператор ввімкнув модуль автопілота, але тимчасово забрав керування дроном на себе, після передав назад до автопілота. Реалізовано через надсилання команд керування, які приймає автопілот та шле дрону. Немає команд керування від оператора = працює автопілот.

3. 03_link_lost_failsafe - Failsafe сценарії, залежно від конфігу дрон або проводить атаку, або переходить в режим очікування, див. файл сценарію. 

4. 04_manual_drop - початок місії на автопілоті, далі оператор забирає керування собі, й керує до кінця місії, та самостійно шле команду скиду.

5. 05_never_enabled - оператор не включив модуль автопілота, керує самостійно.

## Запуск сценаріїв

Всього є три варіанти запуску, на хості, на залізі, та на хості з імітацією роботи з залізом.
Для зручності є окремі .sh скипти які роблять запуск всіх необхідних процесів.
Перед запуском будь якого сценарію необхідно встановити бібліотеку MAVLINK в робочий простір,
```bash
git clone --depth 1 https://github.com/mavlink/c_library_v2.git \
  homeworks/20_autopilot_MAVLINK_course_project/include/third_party/c_library_v2
```
Окрім вказання сценарію треба також вказувати номер тесту (конфігів дрона та цілі), які лежать у homeworks/20_autopilot_MAVLINK_course_project/data/testing_data,  01_sample_circles/02_eliptic_trajectories/etc.

Результат виконання сценарію - файл simulation.json який зберігається на хості, перевірка - http://cppmiltech.com.ua/

### 1. Запуск на хості

1. Зібрати проєкт з кореня репозиторію: `make build-debug`.
2. Запустити `./homeworks/20_autopilot_MAVLINK_course_project/run_host_scenario.sh <сценарій-оператора> <номер-тесту>`, приклад
`./homeworks/20_autopilot_MAVLINK_course_project/run_host_scenario.sh 03_link_lost_failsafe 4`
Усі команди запуску на хості наведено у файлі homeworks/20_autopilot_MAVLINK_course_project/run_host_scenario_commands.txt.

### 2. Запуск на хості з імітацією роботи з залізом

Відмінність цього запуску - імітація передачі даних від дрона до автопілота через UART прямо на хості (через socat + serial_bridge), все інше, теж саме що й звичайний запуск на хості.

1. Зібрати проєкт з кореня репозиторію: `make build-debug`.
2. Запустити `./homeworks/20_autopilot_MAVLINK_course_project/run_bridge_scenario.sh <сценарій-оператора> <номер-тесту>`,

### 3. Запуск на реальному залізі (Raspberry PI + ESP 32)

Автопілот і міст працюють на Raspberry Pi, оператор - окремо на хості. Дрон - ESP32, підключений до Pi трьома дротами (TXD, RXD, GND), живлення обох плат окреме, зі свого USB.

Передумови:

1. Pi і хост в одній локальній мережі (Internet Sharing хоста для USB-гаджета), обидві сторони знають IP одна одної, та можуть спілкуватись через ці IP.

2. На машині, з якої прошиваєте ESP32, встановлено ESP-IDF, і в терміналі активоване його venv-середовище - без цього `idf.py` не знайдеться.
```bash
source ~/.espressif/tools/activate_idf_v6.1.sh
```
У терміналі зʼявиться префікс `(venv)` - ознака, що середовище активне.

3. Прошивка ESP32 зібрана і залита з номером конфігу, який дорівнює номеру тесту, що буде запускатись:
```bash
idf.py build -DDRONE_CONFIG=<номер-тесту>
ls /dev/cu.usb*                              # знайти реальний порт плати
idf.py -p /dev/cu.usbmodemXXXX flash monitor
```
"XXXX" - справжній порт з попереднього кроку, підставити замість плейсхолдера.

4. Код синхронізовано на Pi (rsync копіює разом з ним і склоновану бібліотеку MAVLink):
```bash
rsync -av --exclude 'firmware/' --exclude 'build/' --exclude '__pycache__/' \
  homeworks/20_autopilot_MAVLINK_course_project/ <ssh-адреса вашої Raspberry PI>:~/HM-20/
```

5. Зібрати потрібні цілі на Pi. "-j1" бажаний у кінці, якщо у вас одноядерна слабка PI (наприклад PI Zero 1.3, 512мб):
```bash
cmake -S ~/HM-20 -B ~/HM-20/build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build ~/HM-20/build --target hm20_serial_bridge hm20_autopilot -j1
```

Запуск (два термінали):

1. На Pi: `cd ~/HM-20`
2. `./run_hardware_pi.sh <номер-тесту (1..10)> <ip-хоста>`. Скрипт сам перезавантажує ESP32 (ручний RESET не потрібен) і піднімає міст з автопілотом. Чекаємо рядок READY.
2. На хості, після READY: `./run_hardware_operator.sh <сценарій> <номер-тесту> <ip-pi>`.

Результат - файл simulation.json у корені репозиторію на хості, там, де запущено оператора, перевірка - http://cppmiltech.com.ua/

# Трохи про структуру коду

### Ключові сутності

- Codec - упаковка і розбір усіх MAVLink-повідомлень протоколу (heartbeat, телеметрія, RC override, координати цілей, повідомлення про скид, завершення місії, крок симуляції тощо).
- MissionProcessor - головний цикл ухвалення рішень автопілота: тримає поточний стан наведення і формує черговий крок симуляції.
- MavlinkEndpoint - збирає байти з ILink у готові mavlink-повідомлення і навпаки, пакує повідомлення в кадр для відправки.
- DroneNode - платформонезалежна логіка дрона: фізика руху, обробка вхідних команд, формування телеметрії. Використовується і в drone_sim на Linux, і в прошивці ESP32.
- DronePhysics - фізична модель руху дрона: позиція, швидкість, курс за заданим сигналом керування.
- TableSolver - балістичний розрахунок точки скиду за таблицею.
- JsonTargetProvider / CachedTargetProvider - джерела координат цілей: перше читає їх із файлу сценарію, друге кешує останні отримані координати на боці автопілота.
- FileConfigLoader - завантаження конфігів дрона і боєприпасу з JSON.
- SerialBridge - пересилання MAVLink-кадрів між UART і UDP.
- AuthorityStateMachine - хто зараз керує дроном: автопілот, оператор вручну, чи ніхто. Також відповідає за реакцію на втрату зв'язку з оператором.

### Ключові абстракції

- ILink - транспорт для сирих байтів. UdpLink на хості, SerialLink для UART з боку Linux (Pi), EspUartLink для ESP-IDF. Завдяки цьому один і той самий код (MavlinkEndpoint, DroneNode) працює і на хості, і на залізі, не знаючи деталей транспорту.
- IDroneOutput - куди DroneNode віддає результат своєї роботи (надіслати повідомлення, повідомити про скид чи завершення місії). Реалізація своя для кожної платформи.
- IDroneState - один стан машини наведення, знає умову переходу до наступного стану і яку команду віддати дрону в поточному.
